# tinyray

**一本通讯录，加一次点名。** 给异步 ML 作业用的成员关系层。

它不启动进程、不分配 GPU、不搬运 tensor。它只回答三个问题：
**谁在？还活着吗？我该找谁？**

## 文档

| 文档 | 内容 |
|---|---|
| [01-why.md](01-why.md) | **为什么** —— 问题、真实代价、现有工具为何不合身、事故与原则 |
| [02-design.md](02-design.md) | **是什么** —— pool 策略、边界与调用、scale 与保证 |
| [03-plan.md](03-plan.md) | **怎么做** —— 计划、未测项、已定决策 |

重心在前两篇。**「怎么做」是计划，不是承诺** —— 允许写「待定」，而且鼓励写。

## 这一版与前两版的区别

前两版都失败了，病因不同：

**第一版太长。** 20 篇文档、17 节的模块模板，每篇 300 多行。
读的人找不到重点，写的人也不知道自己在论证什么。

**第二版顺序反了。** 先写「怎么做」，把接口、字段、默认值定死，再回头补测量。
结果压测一跑，`lookup` 慢了 3,600 倍，写好的规格全作废。

**这一版：三篇文档，先说清为什么和是什么，所有数字先测后写。**

## 写文档的规矩

- **每篇只有三节：为什么 / 是什么 / 怎么做**，篇幅约 4 : 4 : 2。
- **每个数字必须标来源**：**实测**（benchmark 跑出来的）/ **推导**（算式可复算）/
  **待测**（冻结设计前必须拿到）。**没标注的数字是伪装过的猜测。**
- **正文中文，代码和标识符英文。** 代码注释也是英文 ——
  一个仓库混两种语言更糟。
- 固定术语保持英文：Pool、Slot、Incarnation、Lease、Registry、fencing、
  readiness、membership。
- **能用大白话就别用术语。**「合唱团少一个人全体卡住」比
  「collective 语义下单成员故障导致组内阻塞」好懂。

## 经验基础

这一版的设计建立在实测上，不是推演。全部数据来自 commit `fc22a16`，
24 核 / 216 GB 单机、loopback。

| 指标 | 实测 |
|---|---|
| heartbeat（h2c） | **57,039 ops/s** |
| lookup(8)（h2c） | **30,370 ops/s** |
| p99 @ 256 并发 | 8.04 ms |
| 10 万成员存储 | ~20 MB |
| 规模敏感性 | 1k → 10 万成员，吞吐**不变** |

压测过程中找到并修掉两个严重 bug —— 两个的**功能测试全程是绿的**：

1. `lookup` 每次跑一遍 O(N) 清扫，10 万成员时慢 **3,600 倍**
2. HTTP/1.1 连接 churn 导致端口耗尽，128 并发时 **0 ops/s，服务端 CPU 0%**
