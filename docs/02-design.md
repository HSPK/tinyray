# 是什么

> 提案；当前未实现。

## 1. 它干三件事

1. **谁在？** 每个进程启动时自己报个到
2. **还活着吗？** 每隔几秒说一声，不说就当没了
3. **我该找谁？** 查通讯录，只查你需要的那几个

**它不替换任何东西。** Slurm、torchrun、Megatron、SGLang 全都留着，
每个进程只加一行。

东西只有一个：**`tinyray` 这个 Python 包**。`pip install` 之后客户端和注册中心
都有了 —— 注册中心就是包里那个同名命令，不是另一个要单独编译和分发的产物：

```bash
pip install tinyray
tinyray --listen 0.0.0.0:8760
```

### 三个词：pool、slot、incarnation

| 词 | 大白话 | 例子 |
|---|---|---|
| **pool** | 一群人 | `"engine"` |
| **slot** | 一个**带编号的座位** | `3` |
| **incarnation** | 这座位上的**第几任** | `#7` |

`engine/3#7` 念作：engine 那群人里、3 号座位、第 7 任。

**座位不是人。人会走，座位还在。** 进程挂了，替补接的是同一个座位。

有些东西必须认座位 —— trainer 的 3 号找错人，NCCL 直接死。
有些完全不用 —— **根本没有「3 号 env worker」这回事**，谁都行。

**座位号 tinyray 不发，只登记。** 号是 launcher 早就给好的：
`RANK`、DP 编号、shard 编号、K8s StatefulSet 的序号。

**为什么还要「第几任」？** 一台机器卡了 30 秒被当成死了，替补坐上 3 号，
然后老进程又缓过来 —— **它也觉得自己坐在 3 号**。有了任期号，
收消息的一方能分清：`#6` 发来的东西，在 `#7` 上任之后**直接拒收**。

### 它不做什么

| 不做 | 谁做 |
|---|---|
| 拉起进程、分配 GPU | Slurm / Kubernetes / torchrun |
| 搬 tensor、权重、流式 token | NCCL / UCX / HTTP |
| task、sample、model version 是**什么意思** | 你的应用 |

tinyray 知道「engine/17 说自己没准备好」，但不知道 model version 是什么意思。
**它给你工具，怎么用你定。**

## 2. 全部 API 和数据结构

### 要记的名字：13 个 + 3 个异常

| 在哪 | 名字 | 干什么 |
|---|---|---|
| 模块 | `join` | 报到，拿到自己的身份 |
| | `pool` / `apool` | 拿到一群人的视图（后者是 async 版） |
| Member | `ready` | 挂个牌子：我能接活了，顺带写上状态 |
| | `leave` | 主动走人，替补不用等租约过期 |
| Pool | `pick` | 要一个能用的 |
| | `slot` | 要 3 号座位那个 |
| | `all` | 要全部能用的 |
| | `epoch` | 把名单冻住 |
| Handle | `url` | 逃生口：流式、大包、长任务自己发 |
| | `label` | 短身份，给日志看（`identity` 是精确的 fencing 令牌） |
| | `timeout` | 改这一次调用的超时 |
| Epoch | `members` | 冻住的那份名单 |
| | `valid` | 这份名单还作不作数 |
| 异常 | `Unreachable` / `Fenced` / `RemoteError` | 见 §5 |
| | `Stale` / `SeatTaken` / `NotFound` | 断线开轮 / 座位被占 / 找不到人 |

```python
import tinyray

# ── 报到 ───────────────────────────────────────────
me = tinyray.join("engine", policy="serving", slot=3, serves=svc)
me.ready(model_version=17)
me.leave()                        # 或者 with tinyray.join(...) as me

# ── 找人 ───────────────────────────────────────────
p = tinyray.pool("engine")
p.pick(model_version=17)          # 要一个活着的、装了 17 的
p.slot(3)
p.all(model_version=17)
p.epoch(min=6)                    # min 不写就等齐 size 个

# ── 调用 ───────────────────────────────────────────
h = p.slot(3)
h.assign(task)
h.assign.timeout(5)(task)
h.url
```

注册中心的地址从 `TINYRAY_REGISTRY=host:port,...` 读，不占名字。

### 数据结构：6 个

**线上跑的只有两条消息**，全系统没有第三种格式：

```python
Beat:                             # 我发出去的
    pool, slot, incarnation       # 我是谁
    policy, size                  # 第一个报到的人定下，后面不一样就报错
    url, state, ready, leaving    # 我的牌子上写了什么
    watch: list[str]              # 我想看哪几群人
    seen:  dict[str, int]         # 我手上这几份名单是第几版

BeatAck:                          # 回给我的
    ttl_ms
    accepted: bool                # false = 你的座位被别人接了，退出吧
    pools:    dict[str, PoolDelta]
```

```python
PoolDelta:
    version: int                  # 第几版：用来算你落后了哪些
    roster:  int                  # 名单指纹：用来看还是不是这批人
    policy, methods, size
    changed: list[Member]         # 只回你还没见过的
    removed: list[int]
    full:    bool                 # true = 你落后太多了，这是全量
```

```python
Member:                           # 你看得到的
    slot, incarnation, url, state, ready
```

在名单里就说明它活着，所以没有 `alive` 字段。

**服务端自己多存一个到期时间，你永远看不到它。**
它要是也算进版本号，那每个人每次心跳都会让版本号涨，
**于是每个人每次心跳都收到一份全量名单** —— 这正是上一版
8,192 个 worker 传 **2.275 GB** 的老 bug。谁过期了由服务端判断，放进 `removed`。

**本地两个对象**：

```python
Handle:  slot, incarnation, url, state, <方法名> → 调用代理
Epoch:   members: list[Handle]
         valid:   bool          # 现在的名单指纹 == 冻住时的指纹
```

### 为什么要两个数字

举个具体的：**trainer 那群人有 128 个，5 号报了一句 `ready(step=100)`。**

现在两个地方要判断「变了没有」：

| 谁在问 | 该答什么 | 答错的后果 |
|---|---|---|
| **缓存**：我要不要更新手上的信息？ | **变了** | 别人永远看不到进度 |
| **名单**：这份名单还作数吗？ | **没变** | 128 张卡白跑一轮 |

**同一件事，一边要算「变了」，一边要算「没变」。一个数字说不了两句话。**

而且第二个**不该是个计数器**。计数器要靠人记得加 —— 以后往 `Member` 里
加个 `last_error`，写代码的人得停下来想「这算不算人变了」。
想错了不会报错，要等到某次训练平白作废才发现。

**名单指纹是算出来的**，只看座位号和任期号：

```
指纹 = hash(座位1,任期1) XOR hash(座位2,任期2) XOR ...
```

以后加多少字段都不会算错，因为它们根本没参与计算。
XOR 是自反的，所以进来和出去是同一个 O(1) 操作，不用重算整份名单。
**只有认座位的 pool 才需要维护它**，`churn` 和 `serving` 从来不冻名单。

### 几条说死的行为

- `pick()` 找不到人**报错**，不返回 `None`。
- `slot(k)` 的人不在**报错**，绝不悄悄换一个人给你。
- `ready()` **不给任何人发消息**，只写在自己身上，随下一次心跳捎过去。
  想让某个人马上知道，就直接调他的方法。
- 不给 `size()` / `count()`。要数数就 `len(p.all())`。

## 3. join 之后，你的进程里多了什么

三样东西，第三样是可选的：

```
一个 Python 进程
├─ 主线程         你的代码（Megatron / SGLang / agent）
│                 ↑ 可能长时间占着 GIL
├─ [Rust] 固定 2 个系统线程
│   ├─ 心跳        不碰 Python，GIL 归谁跟它无关
│   └─ 名单缓存    存在 Rust 那边的内存里
└─ [Python] 一个小 server + 线程池
               只在你给了 serves= 时才有
```

**只有心跳必须是 Rust。** 收调用那部分留在 Python ——
拦掉一个过期调用是罕见的错误路径，而正常调用要进 Python 照样得拿 GIL，
写成 Rust 几乎不省什么。

**不给 `serves=` 就不起 server，连端口都不占。**

### 为什么不能用 Python 线程

这是用 Rust 的**唯一理由**。

Python 线程要跑任何一行代码，都得先拿到 GIL。假设主线程正卡在
`dist.all_reduce()` 里 —— Megatron **通常**会把 GIL 放开，心跳线程能跑。
但碰上一次长时间垃圾回收，或者一段纯 Python 的重活，**心跳就是跑不了**。

停的时间超过租约，这个 rank 被当成死了。它是 `collective` 的成员，
**后果是整轮训练作废**。

Rust 起的是系统线程，**只要它不去调 Python，主线程在干嘛跟它没关系**。
心跳不调 Python。**实测**：抢 GIL 的时候，系统线程只慢 **1.04 倍**，
Python 发起的慢 **49 倍**。

一句话：**「再忙也必须能应答」的放 Rust，剩下全放 Python。**

（也想过起个独立的小进程。放弃了：方法调用要跨进程传参数，
又绕回序列化；而且那个小进程被 OOM killer 干掉，主进程根本不知道。）

### 心跳只证明「进程还在」

必须说清的边界：**它证明进程还在，不证明进程还在干活。**
主线程陷进一个 Python 死循环，Rust 线程照样按时发心跳。

**我们试过补这个洞，实测之后放弃了。** 做法是让 Python 侧起个线程定期「盖章」，
把「解释器多久没动了」一起报上去。问题是**盖章线程自己会被 GIL 饿死**：

| CPU 密集线程数 | 盖章间隔设 200 毫秒，实际观察到的中位 | 最大 |
|---|---|---|
| 1 | 205 毫秒 | 205 |
| 8 | 577 毫秒 | 1,460 |
| **16** | **949 毫秒** | **3,870** |

**一切正常的时候它就能飙到 3.9 秒。** 它的误报比它要抓的故障更常见 ——
而误杀正是我们批评别人的那个毛病，不能自己再犯一遍。

那卡死的进程谁来发现？**调用超时。** 调它超时 → 拿到 `Unreachable` → 换一个。
系统本来就会自愈。

> **tinyray 回答「这个进程还在吗」。**
> **「它还干活吗」由调用超时回答 —— 那是应用的事。**

想证明「业务真的在推进」只有一个办法：**应用自己报**，
比如每步调一次 `me.ready(step=N)`。没有任何自动机制能替它做这件事。

**但绝不能拿它当 barrier 用 —— 不是慢，是做不对。**
`state` 是「此刻的值」，不是「到过哪些地方的日志」。实测：三个 rank 各自
`ready(step=N)` 然后等所有人到齐，rank1 看到人齐了、通过、离开；
rank0 再去看时只剩两个人，**rank1 曾经到过 step 2 的证据已经蒸发了**，
于是它永远等不到。

barrier 要的是单调的证据（「到过至少 N」），通讯录给的是当前快照。
**这两样东西不匹配，换什么写法都补不上。** 要同步就用 NCCL。

### 所以 collective 的成员几乎不该暴露方法

心跳在 Rust 那边，**进程再忙也一定应答**；
你的业务方法要 GIL，**卡在 Python 里就答不了**。
所以一个 trainer rank 卡在 `all_reduce` 里的时候，
它**活着，但你叫不动它**。

rl-bridge 正好印证 —— 它的角色表里 Trainer worker「无独立 HTTP」，
只有管着 dispatcher 的那几个 rank 才起 server。
它们能工作是因为 Megatron 在 C 扩展里放开了 GIL，**这是运气，不是设计**。

**那 trainer 收 batch 怎么办？batch 根本不走这一层。**
rl-bridge 是先发一条元数据，**然后用 `dist.send` 发三段张量**。
HTTP 上走的只有那条元数据。

### 四个容易踩的坑

- **Rust 那边的线程数写死成 2。** 它默认等于 CPU 核数 ——
  在 128 核的机器上就是 128 个线程跟你抢 CPU。
- **端口填 0，让内核分。** 拿到实际端口再写进注册记录。
  少一个配置项，也不会撞端口。
- **fork 之后必须重新 join。** `fork()` 只保留调用它的那个线程，
  Rust 的线程全没了。**PyTorch DataLoader 开 `num_workers>0` 就会踩这个。**
  用 `os.register_at_fork` 把旧的标成失效，**让它明确报错，而不是悄悄卡住**。
- **走的时候发一条带 `leaving` 的心跳**，替补马上能上，不用等租约过期。
  被 `SIGKILL` 就没这一步，靠租约兜底。

## 4. 四种人，四套管法

### 先拆成三个问题

一开始只有三种，但 Dispatcher 没地方放 —— 它挂了不用叫停全场（像 serving），
可你必须找到 DP 3 那一个（像 collective）。**「谁受影响」和「怎么找人」
是两件事，得分开问。**

| 问题 | 几种答案 |
|---|---|
| **换个人行不行？** | 谁来都行 / **必须是坐那个座位的** |
| **少一个，别人受影响吗？** | 不受 / 记一笔 / **全体停** |
| **怎么算「能用」？** | 心跳还在 / 还得自己报状态 / **得全员到齐** |

| 预设 | 换人 | 少一个 | 能用 | 谁是这样 |
|---|---|---|---|---|
| `churn` | 谁都行 | 不受影响 | 心跳还在 | env worker |
| `serving` | 谁都行 | 记一笔 | 自己报状态 | SGLang engine |
| `stateful` | 认座位 | 记一笔 | 自己报状态 | dispatcher / replay buffer |
| `collective` | 认座位 | **全体停** | **全员到齐** | trainer rank |

`stateful` 就是原来漏掉的那一族：**认座位，但不用叫停全场。**

**「只能有一个」不用第五个预设**，但要注意默认语义是**后来者居上**：
一个重启的 rank 必须能抢回自己的座位，哪怕死掉那个的租约还没过期。
选主要的恰好相反，所以它得显式要 `exclusive=True` —— 座位有人就拒绝，
等租约过期再来。

### 两条不能破的规矩

**认座位的，不许偷偷换人。** 座位空着就报错。悄悄给你另一个人，
比报错糟得多 —— 数据写错地方，你还查不出来。

**登记的是进程，不是任务。** 一个 env worker 长期在跑，
里面跑成千上万个 sandbox。**登记 worker（几千到几万），
不登记 sandbox（几十万）**，不然通讯录直接被淹。

### 为什么要「把名单冻住」

**主要原因跟故障没关系，是每次启动都会遇到的问题。**

`p.all()` 给的是「此刻还活着的人」。两个 rank 隔 50 毫秒调用它，
中间刚好有人租约到期 —— 3 号看到 128 个人，5 号看到 127 个。
**两边拿着不同的名单去建 process group，NCCL 当场死锁。**

collective 要的不是「一份活人名单」，是**所有人手上是同一份**。

```python
me = tinyray.join("trainer", policy="collective", slot=RANK, size=WORLD_SIZE)

ep = tinyray.pool("trainer").epoch()   # 等，直到人齐
build_process_group(ep.members)        # 这时每个 rank 拿到的必然一样
```

注册中心只在 `size` 个座位坐满时才发名单，**指纹一样就是「大家看的是同一份」**。
这也就是 `collective` 那条「全员到齐」的意思 —— 不是「我活着」，是「人齐了」。

### 附带一个好处：有人没了你能知道。但用法极容易写错

**在训练循环里查 `ep.valid` 是没用的。** 走一遍时间线：

```
t=0    7 号被 SIGKILL
t=0+   其余 127 个进入 all_reduce，卡住 —— 等不到 7 号
t=5s   租约到期，ep.valid 变成 False
       但没人读得到，他们全卡在 NCCL 里
```

**出事那一刻，所有人恰好都在到不了检查点的地方。** 正确写法是后台线程：

```python
def watchdog():
    while ep.valid:
        time.sleep(0.5)
    pg._abort()          # 主线程的 all_reduce 会抛出来

threading.Thread(target=watchdog, daemon=True).start()
```

能跑通是因为 **NCCL 阻塞时会放开 GIL**。

它比 NCCL 自带超时多的不是「更快」，是**一个 NCCL 拿不到的信号**：
NCCL 只知道「这次通信超时了」，分不清对方是死了还是就是慢，
所以超时必须长过最慢的正常操作；tinyray 看的是**进程在不在**，
跟通信多久无关，所以 5 秒是安全的。

**但要诚实：你也可以直接把 NCCL 超时调小。** 所以这个好处有多大，
**取决于你的超时被迫设多长** —— collective 路径里有存 checkpoint 的价值就大，
否则就小。

### 联系不上注册中心的时候

**不让你判断，让危险的操作自己失败：**

| 操作 | 断了的时候 |
|---|---|
| `pick()` / `all()` | **照常用缓存** —— 这是说好的降级 |
| 已经冻住的 `ep.valid` | **保持 True** —— 128 个人都活着，group 好好的，凭什么杀它 |
| **`epoch()`** | **报错** —— 拿过期名单建新 group，各家可能对不上 |

**已经建好的不动，要新建的拒绝。**

想知道自己是不是断着，看 metric `tinyray_last_beat_age_seconds`，
**不给 API** —— 一个要求十五个地方记得先查的标志位，会被十四个忘掉。

### 异步 DP：两层 pool，不用加预设

一个全局的 collective 池表达不了异步 DP —— 那意味着任何一个 rank 挂了全场停。
拆成两层就行：

```python
tinyray.join(f"dp{d}_ranks", policy="collective", slot=local_rank, size=tp*pp)
tinyray.join("dp_groups",    policy="stateful",   slot=d)   # 每组派 rank 0 代表
```

| 层 | 预设 | 少一个的后果 |
|---|---|---|
| 组内 `dp3_ranks` | `collective` | **这一组**作废 |
| 组间 `dp_groups` | `stateful` | 少个座位，**别的组照跑** |

**「整轮作废」还是「用剩下的人接着跑」，不是 tinyray 的区别，是你的选择** ——
它只翻一个布尔值，你看到 `valid=False` 之后是退出还是重新 `epoch(min=6)`，随你。
所以不用第五个预设，只要 `epoch()` 上那一个可选参数。

### push 还是 pull：你自己定

两种都行，因为它俩只是「谁调谁」。但有条规矩可以从上面推出来：

**谁来都行的 → pull；认座位的 → push。**

原因是**队列有多深**。异步 RL 里一次 rollout 的时长能差几十倍，
任务在 worker 的队列里排队的每一秒，它对应的模型版本就更旧一分。
pull 天生队列深度 ≤ 1 —— **任务被领走的那一刻才绑定模型版本。**

| 谁找谁 | 用哪种 |
|---|---|
| dispatcher → env worker | **pull**（env 谁来都行） |
| collector → dispatcher | **push**（必须是我这个 DP 的那一个） |
| agent → engine | **push + 亲和**（按前缀哈希找，复用 KV cache） |
| trainer 之间 | 都不是，走 NCCL |

pull 的经典反驳是轮询太贵 —— 一万个 worker 每秒问 10 次就是 100k 次/秒，
超过实测的 57k。解法是长轮询，而**长轮询在 HTTP/1.1 下等于一万条常驻连接**，
正是实测里把吞吐打到 0 的那个死法。h2c 之后它变成共用少数连接的 stream ——
**这个权衡是被传输层改掉的。**

## 5. 互相调用

### 方法就是普通的类，一个装饰器都不用

```python
class CollectorService:
    def assign(self, task: TaskAssignment) -> TaskData: ...
    def _internal(self): ...            # 下划线开头的不对外

me = tinyray.join("collector", policy="stateful", slot=k,
                  serves=CollectorService())
```

`serves=` 在 `join()` 的时候：扫出不带下划线的方法、读它们的类型标注建一张
检查表、起一个 h2c server、把地址和方法名单写进注册记录。

### `h.assign(task)` 到底发生了什么

```
你这边   查方法名单 → 没这个名字当场报错
         打包成 JSON → 超过 1 MB 直接报错
         POST /call/assign，头里带上 x-tinyray-target: collector/3#7
对方     对一下任期号 → 对不上直接返回 409
         查方法表 → 按类型标注检查参数 → 调你写的那个方法
```

有三处是故意这么做的，不是实现细节：

- **有方法名单，所以 `hasattr(h, "assign")` 是准的。** 上一版的 handle
  见什么都代理，`hasattr` 永远返回 `True`，方法名写错了要等到跑起来才炸。
- **1 MB 上限是「控制面不搬大数据」的强制手段。** 光写在文档里没用，
  得让人**做不到** —— 超了当场失败，而不是悄悄变慢。
- **认任期号在库里拦掉，不在你的代码里。** 一个要十五个调用点记得的检查，会被十四个忘掉。

### 三种异常，分得清「没送到」和「送到了但抛了」

| 异常 | 意思 | 你该干嘛 |
|---|---|---|
| `Unreachable` | 没送到 | 这个操作重复做没关系就重试 |
| `Fenced` | 送到了，但那边已经换人了 | **重新查地址再试** |
| `RemoteError` | 送到了，你的方法自己抛了 | **tinyray 绝不自动重试** |

**只在确定没送到的时候才重试。** 业务异常一律原样抛给你 ——
只有你知道这个操作重复做行不行。

`RemoteError` 带着 `.type` / `.message` / `.traceback`，但**不还原成原来的异常类**，
因为那要求两边都有这个类，是种看不见的耦合。

### 超时和同步异步

```python
h.assign(task)                     # 用这个 pool 的默认值
h.assign.timeout(5)(task)          # 这一次改成 5 秒
```

超时挂在方法代理上，不当关键字参数传 —— 否则对方的方法自己有个 `timeout`
参数就撞了。**精调过的超时不能被统一掉**，rl-bridge 明文写着「每次请求都必须
显式传超时」，那是吃过亏才立的规矩。

```python
tinyray.pool("collector").slot(3).assign(task)          # 阻塞
await tinyray.apool("collector").slot(3).assign(task)   # 异步
```

对方不用区分：`async def` 的方法会被扔到 `join()` 时所在的事件循环上，
同步方法走线程池。**不自己新建循环** —— 你的 httpx client 都绑在你自己的循环上。

### 边界：30 秒、1 MB

这条线是量出来的。rl-bridge 十二条超时策略里，控制面是 2–30 秒，
数据面是 1800–3600 秒，**中间完全是空的**。

超出的用 `.url` 自己发。**永远不会被替代的**：那个假装成 OpenAI 的代理端点、
SGLang 自己的端点、权重同步 —— 这些都是数据面。

底下就是 HTTP，所以 `curl` 排障的本事一点没丢：

```bash
curl -X POST http://collector-7:9000/call/assign -d '{...}'
curl http://collector-7:9000/_methods
```

## 6. 撑得住吗，靠谱吗

### 它撑的是人数，不是卡数

**实测**（24 核机器，压测器与服务端同机）：

| 指标 | 实测 |
|---|---|
| 峰值吞吐 | **327,000 次/秒**，零错误 |
| 峰值时服务端 CPU | **700% / 2400%** —— 瓶颈在压测器，不在它 |
| 10 万成员 | 跑通，订阅方看到全部 100,000 |
| 10 万成员时的 version | **恰好 100,000** —— 空转心跳一次都没算作变更 |

一个真实作业（1,024 GPU 训练 + 512 GPU 推理 + 5,000 个 env worker）：

| pool | 人数 | 心跳 | 次/秒 |
|---|---|---|---|
| trainer | 1,024 | 1 秒 | 1,024 |
| env | 5,000 | 10 秒 | 500 |
| engine | 64（TP=8） | 5 秒 | 13 |
| dispatcher | 8 | 5 秒 | 2 |
| **合计** | | | **约 1,540** |

占实测峰值的 **0.5%**。带宽约 600 KB/秒，而一次权重同步要广播几十 GB
—— **差五个数量级**。

**所以不分层、不分片，也不起第二份。** 见下面「为什么只有一份」。

撑不住的两样：**按任务登记**（会被淹）和**数据面**（本来就不经过它）。

### 内存看的是「成员数 × 订阅者数」

**实测**。这条比吞吐更容易踩：

| 场景 | 成员 × 订阅 | 内存 |
|---|---:|---:|
| 64 个 engine，8 个 dispatcher 订阅 | 512 | **2 MB** |
| 1 千成员，8 个订阅 | 8,000 | 9 MB |
| 1 万成员，8 个订阅 | 80,000 | 86 MB |
| 4 万成员，4 个订阅 | 160,000 | 367 MB |
| 10 万成员，4 个订阅 | 400,000 | **1.5 GB** |
| **8 个成员，2 千个订阅** | 16,000 | **0 MB** |

最后一行是反直觉的地方：**订阅者多不要紧，被订阅的池子大才要紧。**
代价来自「每个新订阅者第一次同步时，服务端把整个池子复制一份」——
池子小，复制两千次也还是小的。

没人订阅时一个成员占 **1.3 KB**。其中一半是 `state`：`{"shard": 3}` 只有一个键，
但底下的 BTreeMap 第一次插入就要占一整个 **632 字节**的叶节点。

**危险线：乘积超过 10 万要留意，超过 40 万就该改结构。**
改结构通常不是加机器，是**把订阅方向倒过来**，或者别把上万个东西塞进同一个池子。

这也是推荐 pull 的原因之一：一万个 agent 订阅 8 个 dispatcher，乘积只有 8 万；
反过来要 86 MB，而且 **pull 模式下那个上万人的池子根本没人需要订阅**。

**规矩：人多的 pool 只能被少数人看。**
破了不会报错 —— 只会内存爆炸，而且分配器不把它还给系统。

### 为什么只有一份

**因为挂了本来就不贵，而多起几份要付的代价比省下的多。**

它没有需要恢复的东西 —— 所有记录都是各人每个周期重新说一遍的。
所以杀掉再拉起，**一个心跳周期之后自己长回来**（**实测**）。
期间已经连上的照常工作，查地址走本地缓存。
「注册中心挂了」不是一次故障，是一个十几秒的空窗。

而多起几份要解决一个很难的问题：**增量同步的游标是每份各自递增的**。
客户端手上记着「我在第 100 版」，切到另一份（它在第 7 版）之后，
那边找不到第 100 版之后的变更，于是**什么都不发，客户端的缓存就此冻住**，
而且没有任何报错。要修就得给每份注册中心一个身份，客户端发现换人了就丢弃全量重来。

**这些代价换来的，只是把十几秒的空窗变成零。** 不值，所以不做。
`TINYRAY_REGISTRY` 只接受一个地址。

### 保证什么，不保证什么

| 保证 | 凭什么 |
|---|---|
| 注册中心**挂了**，已经连上的照常工作 | **实测**：杀掉它，训练不受影响，各人靠缓存互相找 |
| 不会分裂成两派，不会抢着当老大 | 只有一份，没有共识，没有日志，没得可分裂 |
| 不会有两个进程冒充同一个座位 | 认任期号，而且在 transport 层强制 |
| 绝不无限期卡住 | 每次等待都有期限 |
| 数据丢光了会自己长回来 | 各人每个周期重新说一遍 |

| 不保证 | 为什么能接受 |
|---|---|
| 强一致 —— 会读到过期地址 | 认任期号让它是安全的。但不白拿：调用会失败，得重查再试 |
| 广播一定全都到 | 要求全都到，等于要求失败（单次 99.9999%，做 500 万次全对的概率是 0.67%） |
| 一件事只做一次 | 重复做会出问题的操作，不重试 |
| 拦住两个进程抢同一张卡 | 没有账本就拦不住，那该调度器管 |

### 多久发现有人没了：按 pool 定

trainer 挂了每多等一秒就在烧全组 128 张卡，env 挂了等一分钟也没人在乎。

| pool | 心跳 | 租约 |
|---|---|---|
| `churn` | 10 秒 | 60 秒 |
| `serving` / `stateful` | 5 秒 | 20 秒 |
| `collective` | 1 秒 | 5 秒 |

**这张表自己跟自己有矛盾**：collective 想早点发现，但它的动作是叫停全场，
一次长时间垃圾回收就可能误判，代价是整轮作废。
**这个平衡点没有在真实负载上验证过。**
