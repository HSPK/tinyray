# 怎么做

> 计划，不是承诺。这里的「待定」是有意留的 ——
> 写下「还不知道」比编一个默认值诚实。

## 1. 极简靠的是拒绝，不是压缩

先写死不做什么。**每一条都是省下几百行的地方：**

| 不做 | 用什么代替 |
|---|---|
| 配置文件解析 | 全部走环境变量，一个 `--listen` 参数 |
| 自己的序列化和校验 | Rust 用 `serde_json`，Python 用 `msgspec`（直接从类型标注校验） |
| protobuf / IDL / 代码生成 | 方法签名就是接口，运行时读类型标注 |
| 自己的重试库 | 只给三种异常，重不重试是调用方的事 |
| 日志框架 | `tracing` 默认输出 |
| dashboard / UI | 一个 Prometheus 文本端点，约 20 行 |
| 持久化 | 没有。所有记录每个周期由本人重说一遍 |
| TLS / 认证 | v1 不做，集群内网 |
| 连接池管理 | h2c 多路复用，本来就只要几条连接 |

**rl-bridge 手写了一个 TypedDict 运行时校验器（56 行），那是「需要但没有」
的产物。我们不重复它，直接用 `msgspec`。**

## 2. 代码大小

行数按去掉注释和空行计。

这里原本是一张 2,000 行的预算表，由一条测试盯着，超了就红。它挡下过一次
真的膨胀：预算 1,280 时实际长到 1,641，而超出的部分全在 Python 层。

刹车已经拆了。原因不是它没用，而是它开始挡住该做的事——身份、fencing、
RPC 结果语义、有界并发，这些都是补窟窿，不是加花样，却要为一个行数争论。

**约束没有消失，只是换了形式：精简、高效，靠 review 守，不靠计数器守。**
判据仍然是同一句——*超出预算就是设计错了，不是写多了*——只是现在得有人
把这句话说出来，不再有测试替他说。

## 3. 三个里程碑

每个都有**能跑的验收条件**，不是「写完了」。

### M1 通讯录（约 700 行）

registry 的 beat 处理、TTL 游标清扫、Rust 心跳与缓存、
Python 的 `join` / `pool` / `pick` / `slot` / `all` / `url`。
策略先只做 `churn` 和 `serving`。

**验收**：起 1,000 个假进程互相找到；然后**把 registry 全杀掉**，
它们仍然能靠缓存互相找到；重启 registry，一个心跳周期后名单自己长回来。
另外一条硬的：**让一个进程的主线程占住 GIL 10 秒，心跳一次都不能断。**
这是整个 Rust 决策的验收点 —— 断了就说明 Rust 那部分白写了。

### M2 调用层（约 350 行）

`serves=`、`POST /call/<方法>`、`GET /_methods`、三种异常、
超时覆盖、sync 和 async 两种 handle、任期号校验。

**验收**：把 rl-bridge 的 dispatcher ↔ collector 那一条链路整个换掉，
它原来的 `server.py` + `client.py` + 路由表能删干净，行为不变。

### M3 编组（约 230 行）

`stateful` 和 `collective` 策略、名单指纹、`epoch()`。

**验收**：混沌测试 —— 杀掉一个 slot 再重启，
**旧任期发来的调用被明确拒绝**（而不是被当成新的）；
一个 collective 成员被杀，其余成员的 watchdog 在 **5 秒内**看到名单失效。

## 4. 明确推迟的

| 推迟 | 为什么现在不做 |
|---|---|
| 长轮询 | 先做固定间隔心跳。长轮询能把传播延迟从「一个周期」压到「一个 RTT」，但会让 registry 挂上万条常驻 stream，**没测过** |
| `epoch(min=)` 弹性 | 先只做严格模式（等齐 `size` 个）。弹性要等有人真的要 |
| 证明「进程还在**干活**」 | 试过（Python 侧盖章线程），**实测误报比要抓的故障更常见**，砍了。卡死由调用超时兜底 |
| 客户端遵守 `retry_after` | 过载时的重试放大还在，h2c 之后不再崩，但没解决 |

## 5. 已经测掉的，和还没测的

| # | 项目 | 结果 |
|---|---|---|
| 1 | **10 万成员** | ✅ 跑通，订阅方看到全部 10 万，version 恰好等于加入次数 |
| 2 | **峰值吞吐** | ✅ 327,000 次/秒零错误，**瓶颈在压测器** —— 服务端只用了 700%/2400% CPU |
| 3 | **内存** | ✅ 测了，**和预期不符**，见 [02-design](02-design.md)「成员数 × 订阅者数」 |
| 4 | ~~多副本~~ | **砍掉了**。增量游标是每份各自递增的，切换会静默冻住缓存；而挂掉的代价只是十几秒空窗，不值得为它加一套身份协商 |
| 5 | **collective 的 TTL 下限** | ❌ **仍未测**，需要真实 Megatron 负载才能量误判率 |

第 3 条值得单说：文档原本写「10 万成员约 20 MB」，**实测是一个成员 1.3 KB**，
而且订阅大池子的代价按订阅者数线性叠加。**推演出来的数字又错了一次。**

## 6. 已定的几个决策

| 问题 | 决定 | 理由 |
|---|---|---|
| Rust 留不留 | **只留心跳和缓存** | 理由从「数据面要快」改成「GIL 被占住时必须还能应答」 |
| 心跳几个往返 | **1 个** | beat 顺带把你订阅的名单带回来，不用第二次请求 |
| 分层 / 分片 | **不做** | 实测 5.7 倍余量把它从必须降为可选 |
| gRPC / protobuf | **不用** | h2c 已经解决容量；protobuf 的好处是跨语言，现在没这需求 |
| 第一个真实用户 | **rl-bridge** | 没有真实用户的完美设计，我们做过两版了 |

## 7. 还没想清楚的

- **`POST /task` 幂等吗？** 它现在被无限重试 300 秒。原则说不能重复执行的
  操作不重试 —— 迁移会强制回答这个问题。
- **engine 的一个 TP 组算一个成员还是多个？** 倾向一个，但 PD 分离会打破这个假设。
- **跨 pool 的背压不定义。** trainer 慢了 engine 该不该减速，异步 RL 里
  答案不唯一，tinyray 不替你决定。

## 8. 三个赌，各写明什么算输

**赌一：四个预设够用。**
输的标志是出现一种负载，**用那三个问题描述不出来**。
到那时该加的是「问题」，不是「预设」—— 加预设只是把问题往后推。

**赌二：agentic RL 会把 env tier 的规模推上来。**
12 个团队都选择把这层写进自己代码里，这是个反面信号。
输的标志是：两年内没有人的 env tier 超过一万个进程。

**赌三：接进去会变简单。**
输的标志最明确 —— **rl-bridge 接完之后没有变简单。**
这是最硬的判据，也是为什么第一个用户必须是它。
