# 基准

`bench.py` 量数字，测试断上界。两者不是一回事：测试只在越界时才响，所以东西
可以慢一倍还是绿的 —— 而且真的发生过。`join(timeout=)` 把整份预算交给首拍，
让丢包链路的测试从 7:22 变成 17:06，**全程通过**。

```bash
python bench.py                       # 表格
python bench.py --json out.json       # 机器可读
python bench.py --only rpc_latency    # 只跑一项
python bench.py --check               # 对着 bench-baseline.json 比，退化就非零退出
python bench.py --only point_lookup rpc_batch
python bench.py --only discovery watch_wakeup --coalesce-ms 1
```

每个场景都做特性探测：这一份脚本要能跑在老 wheel 上，做不到的报 `n/a` 而不是
崩掉，否则没法跨版本比。

已知缺失的功能标记为 `unsupported`；执行失败则报错并非零退出。`--check` 还会
拒绝缺失指标、空比较、旧基线格式和不同的工作负载设置，不会把失败测量当成变快。
即使用 `python -O`，实际调用和资源清理也不会被优化掉。

格式 2 记录 Python/原生版本、库指纹、基准脚本 revision、参数和机器信息。场景
或校准硬件改变后，用 `--json` 重录基线；低延迟参数不能和默认参数的基线混比。

`rpc_latency` / `rpc_throughput` 保留历史上的同进程拓扑；独立服务进程用
`rpc_latency_separate` / `rpc_concurrency`。`rpc_batch` 比较同样的 32 项逻辑
操作逐个调用和合成一批的代价，不混淆请求数与操作数。`point_lookup` 使用最多
5,000 个成员的稳定座位池；`all_filtered_ms` 和 `pick_filtered_ms` 各量自己的操作。

默认 50 ms 合并预算是请求量与延迟的取舍，不是网络下限。`discovery` 量突发变化，
`discovery_spaced` 每 150 ms 变一次；显式调整 `coalesce_ms` 再比较不同策略。

注册中心的独立测量可构建运行 `crates/tinyray-registry/examples/perf_registry.rs`。
它明确区分拥有数据的应答组装与 HTTP/共享应答，不把前者冒充端到端吞吐。

## 基线

当前格式 2 基线取三个独立优化版运行的逐指标中位数，再用两次独立运行核对；
23 项受监控指标两次都通过。相对容差仍为 20%，叠加按噪声校准的绝对下限。
亚毫秒 `flush()` 的绝对下限现为 0.1 ms，不再沿用历史上的 50 ms。

### 本次优化实测

同一份脚本、Python 3.11.15、同一台 24-vCPU AMD EPYC 机器，顺序运行，不与
测试或构建并发。修前使用保留的 v0.15.0 wheel，修后使用当前工作区。下表查询
数据是三次运行的热缓存中位数。

| 操作 | 修前 | 修后 |
|---|---:|---:|
| 5,000 成员的 `slot()` | 9.211 ms | 0.002034 ms |
| 5,000 成员的无筛选 `pick()` | 9.133 ms | 0.003671 ms |
| 5,000 成员的 `all()` | 9.271 ms | 4.445 ms |
| 1,000 成员的重复字段摘要 | 0.0990 ms | 0.000360 ms |
| 64 KiB RPC 回声 p50 | 1.269 ms | 0.961 ms |
| 默认策略的突发发现延迟 | 50.85 ms | 50.73 ms |

显式设置 `coalesce_ms=1` 的一次测量将突发发现降至 1.22 ms、watch 通知降至
2.24 ms；默认值未改。独立服务进程上，同样 32 项空调用逐个约 20.7 ms，批量
1.12 ms，按逻辑操作计约快 18.5 倍。单次 RPC 仍在约 0.69 ms。

注册中心独立基准中，已同步游标的拥有数据应答组装从 39.4 us 降至 0.58 us，
长历史的新单项 delta 从 2.29 us 降至 0.73 us。另一个 HTTP 探针中，共享约
1 MiB 名单的往返从 3.27 ms 降至 2.84 ms；组装收益不能冒充网络吞吐倍数。

缓存以有界内存换重复读取速度：客户端每个池最多保留两份各 1 MiB 的序列化快照
和一份有界字段摘要；注册中心每池最多八项、保守序列化大小预算 2 MiB 的 delta。
这不是全进程 RSS 上限；冷读和变化后的池仍需重新生成快照。

### 历史噪声校准依据

`--check` 只比一小撮指标，而且**阈值是量出来的**，不是拍的。空闲机器上连跑
五次，看每个指标相对中位数的最大偏离（吞吐那一行是后来补量的）：

| 看的 | 噪声 | 不看的 | 噪声 |
|---|---|---|---|
| `watch_wakeup` p50 | 0.2% | `join_cold_start` p50 | **2306%** |
| `discovery` p50 | 0.4% | `async_call` p99 | 129% |
| `rpc_latency` p50 | 0.7% | 所有 `max_ms` | 24–34% |
| 查找 @1000 | 0.6–1.1% | `update_changed_us` | 33% |
| `async_call` p50 | 2.6% | `idle_beat_rate` | 9% |
| `flush` p50 | 2.9% | 查找 @10 | 量化到 0.001ms |
| 64KiB p50 | 4.4% | 吞吐（见下） | 22% |

阈值 **20%**，约为最吵的受监控项的四倍，另加绝对下限，免得 0.001ms 的量化
噪声乱叫。**吞吐后来被拿掉了**：那 4.3% 是只在一个 build 上连跑五次得出的，
偏乐观 —— 同一个 build 后来六次跑出 815–958，而 v0.10.0 一次跑出 662，两侧
分别是 899 和 901，比自己的中位低 22%。八个受 GIL 约束的线程共用一个客户端
跑五秒，本来就不是个稳得住的量。宽到不乱叫，就宽到放得过真的退化。`join_cold_start` 的中位数被排除是因为它双峰（见下），一次运行落在
哪一峰纯看运气。

验证过两头：拿另外四次独立运行去比基线，**16/16 全过、一条不叫**；注入真实
量级的退化则全部报出 —— RPC p50 慢 25% 报 1 条、查找慢一倍报 7 条、发现延迟
退回长轮询之前报 1 条（+960%）、吞吐掉 30% 报 1 条；而只慢 10% 放过。

**会叫的东西才有人看。** 一份动不动就红的基线会被忽略，那还不如没有。

## 历史跨版本测量

以下表格保留先前数据；`HEAD` 指当时的 checkout，不是当前代码。尤其是其中的
旧 `flush()` 数字，不代表现在的亚毫秒路径。

### 第一组：核心路径

一台机器、一份脚本、每个版本各自构建 wheel 装进同一个干净 venv。ttl 2000ms
（心跳间隔 500ms），全部走 loopback。

| 指标 | v0.6.1 | v0.7.1 | v0.9.1 | v0.11.0 | v0.12.0 | HEAD |
|---|---|---|---|---|---|---|
| RPC 往返 p50 (ms) | 0.735 | 0.733 | 0.744 | 0.762 | 0.697 | **0.675** |
| RPC 往返 p99 (ms) | 1.136 | 1.167 | 1.094 | 1.077 | 0.958 | **0.955** |
| RPC 吞吐 8 线程 (次/秒) | 887 | 872 | 817 | 848 | 872 | 907 |
| 64 KiB 回声 p50 (ms) | 1.390 | 1.409 | 1.459 | 1.429 | 1.349 | 1.360 |
| `all()` 200 成员 p50 (ms) | 0.310 | 0.306 | 0.306 | 0.313 | 0.308 | 0.316 |
| `snapshot()` p50 (ms) | 0.313 | 0.310 | 0.311 | 0.312 | 0.313 | 0.312 |
| `field_digest` p50 (ms) | n/a | n/a | n/a | 0.023 | 0.024 | **0.023** |
| **发现延迟 p50 (ms)** | **541.8** | **100.9** | **51.1** | 51.6 | 51.2 | **51.0** |
| 空闲心跳 (次/秒) | 1.83 | 2.0 | 1.83 | 2.0 | 2.0 | 1.83 |

### 发现延迟是唯一真正动过的一项

541.8ms → 51.0ms，**10.6 倍**，全部来自 0.7.x 引入的长轮询和 0.9.x 的收尾。
0.6.1 那个 541.8ms 就是设计文档说的"结构性地等于一个心跳间隔"，实测坐实了：
间隔 500ms，中位 541.8ms。0.9.1 之后三个版本 51.1 / 51.6 / 51.2 / 51.0，
在噪声里；这些突发变化量到的是 50 ms 合并预算，不能据此断言网络延迟已经到底。

### 其余都是平的，这本身是结论

RPC 往返 p50 六个版本走了 0.735 → 0.675（快 8%），p99 走了 1.136 → 0.955
（好 14%）。方向一致但幅度小，够不上"优化"，只够说"没有变慢"。查找路径
（`all()` / `snapshot()`，200 成员）六个版本全在 0.306–0.316ms 之间，
**没有回归**。这些数字的价值不在于漂亮，在于下次有人动了缓存或分发路径时，
它们会告诉你动了多少。

`field_digest` 从 0.11.0 才有，0.023ms 对 `snapshot()` 的 0.312ms，**13 倍**
—— 这正是它存在的理由：只关心两个键的 watcher 不该为第三个键的变化付一整份
快照的钱。

### 三个必须说清楚的坑

**吞吐 907 次/秒，和文档里的 327,000 次/秒不是一回事。** 后者是注册中心在
`loadgen` 下的心跳吞吐，前者是 Python RPC 路径（8 线程、一个 httpx 客户端、
GIL）。两个数字量的是两个东西，而文档没说，很容易被读成同一条线上的退步。
这里的 907 还包含了与调用方共用 GIL 的服务端，不是独立调用方的天花板。

**空闲心跳每秒 2 次，六个版本一样。** 长轮询省的不是这个。文档里"14.5 次/秒
对 0.12 次/秒"说的是**一个等变化的 watcher**，那是另一个场景，这份脚本目前
没覆盖。别拿这一行去印证长轮询。

**冷启动是双峰的，而且每个版本都一样。** 一次启动要么当场接到答复（约 1ms），
要么等到下一拍（约 42ms），中间没有东西。所以中位数落在哪一档只看比例：
n=10 时它在 1.0 / 21.2 / 41.6ms 之间乱跳，看着像 40 倍的差距；n=40 重测，
v0.12.0 是 25/40 快、HEAD 是 24/40 快，**完全一样**，v0.6.1 是 20/40。
脚本因此报 `under_5ms` / `over_15ms` 而不只报中位数。这一条是自己给自己的
提醒：先怀疑方法，再怀疑代码。

### 第二组：其余 API（v2 场景）

| 指标 | v0.6.1 | v0.9.1 | v0.11.0 | v0.12.0 | HEAD |
|---|---|---|---|---|---|
| RPC 同步 p50 (ms) | 0.733 | 0.748 | 0.763 | 0.695 | **0.671** |
| **RPC 异步 p50 (ms)** | 1.415 | 1.424 | 1.441 | 1.390 | **1.331** |
| 抛异常调用 p50 (ms) | 0.912 | 0.911 | 0.925 | 0.860 | 0.919 |
| `update()` (µs) | 3.0 | 3.0 | 3.0 | 4.0 | 3.0 |
| `flush()` p50 (ms) | 584 | 660 | 689 | 645 | 702 |
| `all()` @1000 成员 (ms) | 1.543 | 1.521 | 1.566 | 1.562 | 1.557 |
| `epoch()` @1000 (ms) | 1.567 | 1.572 | 1.670 | 1.607 | 1.615 |
| `field_digest` @1000 (ms) | n/a | n/a | 0.102 | 0.108 | **0.097** |
| `changes()` 唤醒 p50 (ms) | n/a | 50.99 | 51.18 | 51.02 | 50.98 |
| `fields=` 挡掉 10 次无关变化 | n/a | n/a | 0 | 0 | 0 |

`n/a` 是特性探测的结果，不是失败：0.6.1 的 `changes()` 返回裸生成器（不能当
上下文管理器、也没有 `fields=`），`field_digest` 从 0.11.0 才有。

**异步调用比同步贵一倍，五个版本都是。** 1.33ms 对 0.67ms。这不是回归 ——
它一直如此，只是从来没人量过。差值来自 `httpx.AsyncClient` 那条路加上事件循环
的调度，不是 tinyray 自己的代码，但调用方需要知道：**在 loopback 上，异步版
省的是线程，不是时间。**

**规模曲线（HEAD）：**

| 成员数 | `all()` | `snapshot()` | `all(shard=)` | `field_digest` | `epoch()` |
|---|---|---|---|---|---|
| 10 | 0.018 | 0.017 | 0.006 | 0.001 | 0.020 |
| 100 | 0.140 | 0.142 | 0.026 | 0.009 | 0.148 |
| 1000 | 1.496 | 1.513 | 0.207 | 0.102 | 1.548 |

这些历史批量路径随 N 增长。两个比值值得记住：1000 成员时 `field_digest` 比整份快照便宜
**15 倍**（0.102 对 1.513），八分之一命中的过滤比 `all()` 便宜 **7 倍**
（0.207 对 1.496）—— 后者是因为匹配发生在序列化之前，在 Rust 侧做完。
`epoch()` 只比 `snapshot()` 贵一点点：冻结一轮的代价就是取一次名单。

`changes()` 的唤醒 51.0ms 和轮询式的发现延迟 50.9ms 一样 —— 说明这条路上
花的全是"变化送到本地缓存"，被唤醒本身不要钱。`fields=` 在三个版本上都把
10 次无关变化挡得一次不剩。

## 方法

- 同一台机器连续跑完，机器空闲。**跑基准时不要同时跑测试套件** —— 试过一次，
  两条时间敏感的测试当场变红，其中一条是围栏窗口，负载下有 59 次调用落到了
  本该已被围栏的进程上。
- 每个版本 `git worktree` 检出、`maturin build --release` 出 wheel、装进
  `/tmp/bv`。`bench.py` 始终用工作区里的那一份，所以脚本是常量。
- 共用 `CARGO_TARGET_DIR`，否则每个版本都要冷编译一遍。
