# 为什么

> 提案；当前未实现。

## 1. 三群进程，没人知道它们是一个作业

一个异步 RL 作业里跑着三种完全不同的进程：

```
env      几千台 CPU 机器      跑沙箱、执行工具、判分
engine   几十台 GPU 服务器    模型推理，生成回答
trainer  128 张卡            训练，必须齐步走
```

它们由 Slurm 或 Kubernetes 拉起，各自用 SGLang、Megatron、Docker。
**没有任何东西知道这三群人合起来是一个作业。**

于是每个团队都自己写一遍：谁在、谁还活着、我该找谁、谁被替换了。
12 个团队写 12 遍，其中一份手写的 generation 校验写错了，没人知道。

### 挂了一个之后，正确反应差别极大

**env 挂一个** —— 没人在乎。少一个临时工，活分给别人。

**engine 挂一个** —— 少一个服务窗口，排队变长。得补，但不急。

**trainer 挂一个** —— **全组卡死。** 那 128 张卡在做类似合唱的事：每一步所有人
必须同时到齐。少一个人，剩下 127 个会**永远站在那儿等** —— 不报错，就是干等。

现有工具用**同一种方式**对待所有进程。这是第一个问题。

## 2. 真实代价：一个被架构逼出来的非目标

这不是假想。看 rl-bridge —— 一个已经在跑的异步 RL 框架：

它的全局注册表 `CoordinatorService` **只在 `trainer.global_rank == 0` 上创建**。
为什么？因为总得找个地方放，而 rank 0 刚好唯一。

后果是一条因果链：

```
通讯录寄生在 rank 0
  → 只能开局读一次     文档原文：「再读取一次 /peers」
  → 成员地址不可变
  → 坏节点无法替换
  → 「不在训练中途局部替换坏节点后继续运行」被写进非目标
```

**这条非目标不是产品决策，是架构的必然后果。**

而它恰恰是规模上最致命的一条：卡越多 MTBF 越短
（16,384 GPU 的 MTTF ≈ 1.8 小时，**实测**，arXiv 2410.21680），
「每次故障全局重启」的代价随规模指数放大。

**tinyray 换来的不是「少几个角色」—— 角色一个都不会少。是解锁这一条。**

## 3. 现有工具为什么不合身

### 先把两个流行说法证伪

**「异步 RL 需要万卡编排」** —— 不成立。同行评审的上限是 **1,024 GPU**
（Laminar, arXiv 2510.12633）；AReaL 验证到 512 GPU（arXiv 2505.24298）。
xAI 声称 20 万 GPU，但**仅有博客，无方法可查**。所以「万卡」不能当卖点。

**「Ray 的 GCS 是结构性瓶颈」** —— 也不成立。Ray 的 actor 调用**本身就是点对点
直连**，GCS 只管创建和销毁；它的 O(N²) 资源同步（RFC #57640）**已于
2025-11-20 修复**（PR #57641）；slime 用 Ray 出了 GLM-4.5 到 GLM-5.2。
**我早先反对 Ray 的论据是错的，作废。**

### 真问题是异构，不是规模

env tier 让控制面规模和 GPU 数量**解耦**了：128 张卡的作业，也可能挂着上万个
sandbox 实体。12 个框架里 7 个用 Ray，技术栈已经收敛（SGLang/vLLM +
Megatron/FSDP + NCCL 权重广播），**唯独没有一个东西同时管得好抖动的 CPU 群、
有状态的 GPU 服务、和不容错的 collective。**

| 工具 | 擅长 | 不合身在哪 |
|---|---|---|
| **Ray** | 动态任务图、actor 生命周期 | 无 pool 概念，三群人一视同仁 |
| **Slurm** | 一次性 gang 分配，到 16,384 GPU | 「几千个来去的 CPU worker」不是它的模型 |
| **Kubernetes** | env tier 完美 | collective tier 很差，官方上限 5,000 节点 |
| **Consul / etcd** | 通讯录本身很成熟 | 探针要么在机器上（太粗），要么在 Python 里（会误杀），见下 |
| **各 RL 框架** | 端到端能跑 | 拓扑写死在自己代码里 |

### Consul + gRPC 拼一拼能得到九成，剩下那一成是什么

必须承认：服务发现加 RPC 是个几十年的老类别，用现成的能覆盖绝大部分。

真正的差别在**探针住在哪**。「这个进程还在吗」，
探针放的位置决定了它会犯哪一种错：

| 探针在哪 | 进程死了能发现 | 会不会误杀 |
|---|---|---|
| 机器上（看 Consul agent 自己活着） | ❌ 只证明**机器**没死 | ✅ 不会 |
| **Python 里**（TTL check、HTTP check） | ✅ 能 | ❌ **会** |
| **进程内，但在 Python 之外** | ✅ 能 | ✅ 不会 |

中间那行是最要命的：上报也好、应答也好**都是 Python 代码**。
主线程卡在 `all_reduce` 里的时候它们都跑不了，于是这个 rank 被判死 ——
**整轮训练作废**。tinyray 的心跳跑在 Rust 系统线程上，不碰 GIL，所以不会。

**但要诚实：Consul 的 TCP check 也落在第三行。** 内核完成握手不需要 Python
参与，进程没了端口就没了。所以真实差距只剩两条：

- **不用监听端口也能证明自己在。** trainer rank 不给 `serves=` 就没有端口，
  TCP check 无从检起 —— 你得专门为健康检查开一个。
- **心跳能捎带 ML 状态。** model version、座位、任期都跟着心跳走，
  TCP check 只能给你一个布尔。

其余的差异（座位加任期、按模型版本筛人、冻结名单）都能用 Consul KV 加
gRPC interceptor 自己写出来 —— 只是要写。

### 顺带说一句体量

**实测**（`git clone --depth 1` 后统计，2026-08）：

| | Consul | tinyray 预算 |
|---|---|---|
| Go / Rust+Python 代码（不含测试） | **356,683 行** | **约 1,280 行** |
| 直接依赖 | 111 个 | 个位数 |
| 部署形态 | 每机一个 agent **+** 3–5 台 server 跑 Raft | 一个二进制，起几份都行 |
| 状态 | 要持久化、要快照、丢多数派就写不进去 | **无状态**，各人每周期重说一遍 |

光 `agent/consul` 一个目录就有 68,769 行，里面塞着 Raft 状态机、ACL、多数据中心联邦。

**但「轻」本身不是论据，「轻到一下午能读完」才是。**
出问题时前者你能读完源码，后者你只能提 issue。
而且要诚实：**如果你的集群里本来就跑着 Consul 或 etcd（K8s 自带），
这条论据会弱很多** —— 运维成本已经付过了。

所以定位不是取代 Ray，是**管 Ray 管不好的那一层**。一个用 Ray 管 GPU tier 的
团队，可以用 tinyray 管上万个 sandbox，两者不冲突。

### 一个必须正视的反面信号

**「没人做过」可能是信号，不是机会。** 12 个团队都选择内联，这值得警惕。
我们的赌注是：他们没做是因为规模没到，而 agentic RL 会把 env tier 推上来。
**这个赌注可能输。**

## 4. 只给地址不够

如果 tinyray 只返回一个 URL，样板代码一行都省不掉。rl-bridge 里纯粹因为
「我要调另一个进程」而存在的代码：

| 位置 | 行数 |
|---|---|
| `coordinator/{server,client,types}.py` | 310 |
| `dispatcher/{server,client,types}.py` | 129 |
| `utils/api.py`（envelope、路由助手、**手搓的运行时校验器**） | 317 |
| `utils/http.py`（retry、timeout、client 封装） | 196 |
| **合计** | **~950** |

两个值得警惕的信号：它**手写了一个 TypedDict 运行时校验器**（约 56 行）——
「需要类型化 RPC，但没有，只好自己造」的典型症状；而 `api.py` 的 schema 里
**一半是成员关系类型**（`HealthData` `PeersData` `CollectorMetadata`），
这些本来就不该是应用的类型。

## 5. 原则从哪来

### 先讲一件具体的事

早期有个 readiness 检查，用来回答一个很简单的问题：**「这个 worker 干完了没有？」**

它的实现是：把 worker 算出来的结果整个取回来，看一眼有没有值，然后**把结果扔掉**。

功能上完全正确，测试全绿。直到有人发现，问一句「好了没」要花 **237 毫秒** ——
因为那个结果有 200 MB。改成只问一句状态之后，**0.14 毫秒**。

**答案从头到尾都是对的。错的是代价。**

### 同样的事，前后发生了四次

| 做错的事 | 表面症状 | 真正的原因 |
|---|---|---|
| readiness 把整个结果取回来 | 有点慢，看不出为什么 | 200 MB 走了控制面。237 ms → 0.14 ms |
| 把完整成员名单推给每个 worker | 启动越来越慢 | 名单大小 × 人数。8,192 个 worker 要传 **2.275 GB** |
| 每次查地址，顺手清理一遍过期成员 | 查询慢 | 清理是 O(N)。10 万成员时慢了 **3,600 倍** |
| HTTP/1.1 连接用完就扔 | 并发一高就全部报错 | 端口被 TIME_WAIT 占满，14 秒耗尽。**此时服务端 CPU 是 0%** |

四次的共同点只有一条：

> **测试只问「答案对不对」，从来没人问「这个答案花了多少」。**

四次的答案都是对的，代价错了一千倍。

### 于是有了这七条

每一条的目的都一样：**把代价变成测试能检查的东西，而不是靠人记得。**

**一、控制面只传小消息。**
每个操作有字节上限和时间上限，由测试断言。更大的数据走 NCCL 或存储。

**二、不碰进程已经有的东西。**
不分配 GPU、不占用默认 process group、不改 `CUDA_VISIBLE_DEVICES`。只读，不写。
早期版本占用了默认 process group，结果 Megatron 起不来。

**三、rank 用 launcher 给的，不自己发明。**
从 `RANK` / `SLURM_PROCID` / `OMPI_COMM_WORLD_RANK` 里读。
接入任何框架的第一个问题都是「我的 rank 是多少」。
**这个问题一旦有第二个答案，集成就崩在这里。**

**四、每个身份带一个版本号，收到旧版本就拒绝。**
真实事故：一台机器卡了 30 秒被判定死亡，替补进程拉起来，
然后老进程又缓过来了 —— 两个进程都认为自己是 `engine/17`，
轮流往通讯录里写自己的地址。症状是「偶发超时」，查了很久才找到。

这条有个执行要点：**检查放在 transport 层，让调用方绕不过去。**
一个需要十五个地方都记得的机制，会被其中十四个忘掉。

**五、任何操作都不要求全员到齐。**
全局操作只作用于**当前健康的**成员。
算一下就明白：单次成功率哪怕高到 99.9999%，连做 500 万次全部成功的概率也只有
**0.67%**。要求全员成功，等于要求失败。

**六、失败要有明确期限，绝不无限等下去。**
每次等待都有 deadline，失败信息里写清楚在等谁、等了多久。
同一个死锁我们踩过三次，形状一模一样：
**一个组操作在把任务发给其他人之前，先等了其中某一个。**

**七、能用软状态就别用共识。**
每条记录由它的主人定期重新声明一次。全丢了，一个周期之后自己长回来。
**实测**：把注册中心杀掉，worker 靠本地缓存继续互相寻址，训练没有中断；
重启之后一个心跳周期内自己长回来。

### 这七条同时排除了什么

写下来是为了防止以后慢慢漂回去。以下做法无论看起来多方便，都不做：

- 放一个每轮迭代都要经过的中心节点
- 让成员名单随集群规模一起变大
- 用父子进程关系判断谁还活着
- 把每个 worker 的 lease 放进共识存储
- 提供任何「给我 N 张卡」这类 API
- 设计需要全员成功才算成功的操作
- 对不能重复执行的操作做重试
